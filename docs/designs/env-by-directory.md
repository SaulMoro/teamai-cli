# Team env by directory

> Status: **implemented**. Issue: [#1018](https://github.com/Tencent/teamai-cli/issues/1018).

A process started in a directory gets the team env of the scope that governs that directory, the scope `resolveConfigForDir` resolves. Nothing records a machine-wide "active project", so several projects open at once in separate windows each get their own env, and a workspace (#913) resolves like any other scope.

## Why not one block per scope

Before this, each scope wrote its own `source <env.sh>` block into the shell profile, and the profile kept the user scope's block plus at most one project block (#876). A pull in a project took over another project's block. With several project scopes on one machine, the profile followed whichever directory pulled last: the session-start pull flipped it each time a session opened in another project, and `doctor` failed in every other project. The pull also runs detached, after the agent has started, so the block it wrote never reached that session.

One block per data home would make every project live in every shell, team values of unrelated projects included.

## Contract

| Directory | Loads |
| --- | --- |
| In a project without `inheritUserScope` | the project's `env.sh` |
| In a project with `inheritUserScope: true` | the user scope's `env.sh`, then the project's, only while both scopes are opted in and the project's `env.sh` is present and readable (a key the project declares, as a variable or a secret, is the project's; the project's `env.sh` puts back the member's own value of a declared key it does not export) |
| A linked worktree of a project | that project's, before the worktree has pulled |
| A project no pull has registered yet: set up in its checkout (`.teamai/config.yaml`, or a single-repo project's `.teamai/teamai.yaml`), or marked in its git common directory (`teamai-env-pending`) | nothing |
| Anywhere else | the user scope's `env.sh` |

Secrets never come from the user scope in a project: `env.sh` holds no secret, and `teamai env exec` applies only the governing scope's.

## Mechanism

```text
pull (user scope)    ── registers ──▶ ~/.teamai/env-scopes   user <TAB> - <TAB> env.sh|- <TAB> 0 <TAB> -
                        (and a project pull that inherits it, which writes the user env.sh too)
pull (project scope) ── registers ──▶ ~/.teamai/env-scopes   git|dir <TAB> key <TAB> env.sh|- <TAB> inherits-user <TAB> partition
pull (any scope)     ── new stamp ──▶ ~/.teamai/env-scopes   first line, when the registry or an env.sh changes
pull (any scope)     ── writes ─────▶ ~/.teamai/env-loader.sh
                     ── one block ──▶ $SHELL's profile: ${ZDOTDIR:-$HOME}/.zshenv (zsh) | .bashrc / the Git Bash chain (bash)
                     ── same block ─▶ the other shell's profile of the two, when that shell is installed or the file exists
                     ── same block ─▶ off Windows, bash's login file (first of .bash_profile, .bash_login, .profile; .profile created when none exists), when it sources none of the above

shell starts, or cd in an interactive shell
  └─ loader: git common dir of $PWD (or $PWD outside git) → registry line → env.sh files
             puts back what it set for the previous directory, then sources the new files
```

- The registry key is the git common directory, shared by a checkout and its worktrees, as the project partition is. Outside git it is the directory itself, as `detectProjectConfig` reads `<dir>/.teamai` only there.
- "Outside git" means git did not name a repository and no `.git` entry sits in the directory or above it. When git fails (not installed, a non-zero exit, a broken `.git`, unreadable metadata, a `safe.directory` refusal) under a `.git` entry, the governing scope is unknown and fails closed: the loader loads nothing there and prints nothing, `resolveConfigForDir` reports that `.git` as unreadable, so `env exec` applies no team env, and a project pull there fails to register rather than record a `dir` row. Telling the two apart by a `.git` entry, not git's message, keeps it independent of the locale. A member without git keeps the user scope's env outside repositories.
- On Windows the key is the native path with forward slashes and ASCII letters in lower case (`c:/work/repo`). The loader prints the shell's directory in that same form whichever shell runs it: Git Bash `pwd -W`, else `cygpath -m`, else a `/c/...` or `/cygdrive/c/...` path rewritten to `c:/...`, then lower-cased.
- zsh reads `.zshenv` for every invocation, so the `zsh -c` a tool runs a command with gets the env of its own directory, whatever launched the tool. A `shellProfilePath` override still chooses bash's profile; zsh always uses `.zshenv` (under `$ZDOTDIR` when set), warns if the override names another zsh file, and moves an older block out of that file. bash reads no startup file for `bash -c` except the one `BASH_ENV` names, so the loader points `BASH_ENV` at itself and, in that bash, unapplies the previous directory's env, sources the member's original value with `BASH_ENV` naming that file while it runs (so it can find files beside it), then loads the env, so the team value wins a key both set, in zsh as in bash. A startup file or command that sets the member's own `BASH_ENV` after the loader ran gets it taken back at the next prompt, by bash's prompt hook and by a zsh `precmd_functions` hook that runs first, and that value becomes the one chained.
- The loader exports the directory, the registry's stamp and the files it applied, so a child shell in the same directory outside git does no work until a pull changes the registry or an `env.sh`; a user env that no registry row chose is reused only while the directory still has no project markers. In a checkout the child asks git again, whatever the route, as a `cd` does. It restores whether each overridden key was unset, local to the shell, or exported; only values and markers that were exported before entry pass to child processes.
- A ZDOTDIR the CLI's environment carries is one every zsh started from it inherits, and those read `$ZDOTDIR/.zshenv`, never `~/.zshenv`, so the block goes there.
- `teamai env exec` resolves the same contract for any shell or tool: it drops values another scope's `env.sh` exported (the marker `env.sh` writes identifies them), then applies the user scope's variables when the project inherits it, then the project's. It drops the loader's exported bookkeeping, so a `bash` the command starts does not reapply the previous directory's env over the one `env exec` applied. When the member has a `BASH_ENV` of their own, the command's `BASH_ENV` is `~/.teamai/env-exec-bash-env.sh`: it sources the member's file, with `BASH_ENV` naming that file while it runs, then puts back each key `env exec` set or removed as the command started with it, its value or its absence, so the team value wins a key both set and a removed secret stays unset, as with the loader. A `BASH_ENV` the member's file sets becomes the file it chains to, and `BASH_ENV` points back at it, so a nested `bash` runs it too; the loader does the same. On Windows it also unsets any other spelling of those keys that the member's file set. Without a member `BASH_ENV`, `BASH_ENV` is removed.
- MCP delivery fills a `${VAR}` the team sets nothing for from the process environment by the same rule: a value another scope's `env.sh` exported is not the member's and fills nothing. In Bash the loader routes in the prompt hook, so `cd project-b && teamai pull` still carries project A's values; they never reach project B's MCP configuration.
- A pull in a project that inherits the user scope refreshes the user repo and rewrites the user `env.sh` from it in the same pull, so shells, `env exec` and MCP read one revision. While the user scope's env can't be resolved, whatever the project's state, that pull leaves the user `env.sh` as it is, and `env exec` and MCP apply what it holds too (the user scope's env backup), without a key the project declares ([Failures](team-secrets.md#running-a-cli-with-env-exec)). Only env comes along: the user scope's hooks and MCP servers are still not delivered there.
- A pull writes a scope's `env.sh` (what shells load) and its env backup (what `env exec` and MCP read) together: the backup is written after `env.sh`, and if it fails, `env.sh` is put back as it was, so a failed pull leaves both on the last values.
- An inheriting project's `env.sh` puts back the member's own value of each key it declares and does not export, when the user `env.sh` sourced first set it. On Windows that covers every spelling of the key (`token` for `TOKEN`), as resolution treats them as one variable.
- On Windows, before the loader sources an `env.sh`, it unsets every other spelling of each key that file exports, the member's own included, so the one spelling left holds the file's value. It records what it unset, so leaving the directory puts the member's spelling and value back.
- The loader's key and file lists are split with an `IFS` it sets for that loop, whatever `IFS` the member uses.
- The keys the loader saves, restores and unsets (Windows spellings included) are the ones an `env.sh` assigns. `env.sh` stays POSIX sh, every value single-quoted, so a multiline value spans lines; the loader takes a key from a line that starts `export KEY=` outside a quoted value, never from a line inside one. It runs that scan with the `awk` on the system's default path (`command -p awk`), whatever `PATH` the member set, and does not source a file whose keys it could not read, since nothing could unapply it.
- A project row routes no team env when the project's `env.sh` is missing or unreadable. If any selected env file cannot be scanned, the loader sources none of the selected files, so an inheriting project cannot fall back to user values while its own env is unavailable.
- The block goes in `$SHELL`'s profile, and in the other loader shell's (zsh or bash). A `$SHELL` that is neither (fish) counts as bash only when bash is installed; with neither shell installed, no profile gets the block: a member who starts both, bash from zsh say, gets each directory's env in either rather than keep the directory the second shell started in. Off Windows, that file is created when the other shell is installed (on `PATH`); otherwise, and on Windows, it is used only when it already exists. Off Windows, the bash file is `.bashrc`, which only an interactive non-login bash reads; a login bash (`bash -l`, a macOS Terminal) reads the first of `.bash_profile`, `.bash_login` and `.profile` that exists, and never `BASH_ENV`, so that file gets the block too, unless its `source` chain already reaches one of the files above; off Windows a bash `shellProfilePath` override only picks the file for the mode that file serves, and the other mode follows these rules (an interactive bash's `.bashrc`, created when bash is `$SHELL` or installed, unless its chain reaches a listed file); a file along that chain that already carries the block keeps it. When none of the three exists and bash is `$SHELL` or installed, `.profile` is created: last in bash's order, it shadows no login file the member adds later, where a created `.bash_profile` would shadow their `.profile`. teamai never creates `.bash_profile` or `.bash_login`. Pull writes every one of these files in the same all-or-nothing plan as the older blocks it moves out, `teamai uninstall` removes the block from each, and `doctor` owes it in each.
- Only bash and zsh run the loader. The block can sit in `~/.profile`, which a POSIX sh login shell (dash, ksh) reads too; the loader returns at its first line there, so that shell loads no `env.sh` and does not parse the rest.
- Every loader apply, including calls from prompt and directory hooks, scopes itself against the member's shell options: Bash `allexport` and `nocasematch` are disabled only while it runs, then restored; zsh uses local POSIX-shell options. Loader bookkeeping assignments therefore do not change a member variable's export state or inherit those options' effects.
- The routing hook runs before the member's Bash `PROMPT_COMMAND` and zsh `chpwd_functions` hooks, and the zsh `BASH_ENV` hook before their `precmd_functions`; uninstall takes both zsh hooks out. Bash prompt hooks retain the preceding command's `$?` and `PIPESTATUS`. A scalar `PROMPT_COMMAND` keeps its form and export, and uninstall restores it as it was; a member's later edit such as `PROMPT_COMMAND="$PROMPT_COMMAND; cmd"` keeps one routing hook, still first. zsh's `precmd_functions` hook also routes whenever `$PWD` is not the directory last routed, and puts the `chpwd_functions` hook back, so a `.zshrc` that replaces `chpwd_functions` does not keep the first directory's env. A startup file that replaces bash's `PROMPT_COMMAND` or zsh's `precmd_functions` after the block removes routing until the next shell, as it removes every other prompt hook.
- Loader resolution first unapplies the prior directory's env, so team `PATH` and `GIT_*` values cannot redirect or block registry lookup. Shell startup variables, hooks, and loader state (every name the loader reads or writes: `IFS`, `PWD`, `BASH_VERSION`, `BASH_VERSINFO`, `ZSH_VERSION`, `PIPESTATUS`, any name beginning `__TEAMAI_`, in any case, and the `TEAMAI_ENV_SH_<64 hex>` markers env.sh exports), plus the Bash read-only `SHELLOPTS`, `BASHOPTS`, `UID`, `EUID`, and `PPID`, are reserved across `env.sh`, `env exec`, MCP delivery, and session hints; reserved declarations are warned and ignored.
- Project registry rows carry their partition path so user-scope uninstall can preserve registered machine data without reopening a checkout. Rows without that association, or naming their env.sh or partition by a relative path, are malformed and ignored by both routing and preservation.
- A matching but malformed project row is fail-closed: it blocks user fallback. Registration rejects unsupported paths, unreadable registries, and a registry lock timeout; pull reports the project and fails. An opt-out removes the old profile block before changing the row to `-`, so a failed profile write leaves the prior route intact.
- Pull's env stage runs resolve → write `env.sh` and the env backup → loader and profile → registry row, with a new stamp when `env.sh` changed. Only an env that cannot be resolved changes the row to `-`. A failed write puts both files back; a failed profile write or registration leaves the row as it was, which routes the files this pull wrote; an `env.sh` that could not be put back is registered as `-`. Pull reports each failure and exits non-zero. A registered project keeps its row, and a project with no row yet keeps its pending marker, so none of them gives it the user env unless it inherits it.
- A project whose data lives in `~/.teamai/projects` has nothing in its checkout, so teamai writes `teamai-env-pending` in the checkout's git common directory (the registry key) wherever such a project can exist without a row: when its config is saved there (init), when migration moves a `.teamai/config.yaml` out, and at the start of pull's env stage. Each writer skips a scope that already has a row. A successful registration removes it, and uninstall removes it with the row. Outside git the data home is `<dir>/.teamai`, which holds the config, so no marker is needed.
- With no row for a directory, the loader looks for the pending marker in the git common directory it already resolved, then for the marker the contract names at the top of its checkout (the nearest directory holding `.git`), or in the directory itself outside git, with plain `[ -e ]` tests. The member's own `~/.teamai` is the user scope's, not a marker. The loader treats either file as a project even where `detectProjectConfig` would not (a `teamai.yaml` without `mode: self`); the difference only loads less.
- `doctor` checks the contract where it is used, each part by its own state: an inheriting project's user `env.sh` and the profile block are checked even while the project's own declarations fail; only the comparison with the project's `env.sh` is skipped. While a part can't be resolved, the `env.sh` its last pull wrote is still owed, since pull keeps it and shells load it: a missing one is reported. `This directory resolves its team env` starts the member's `$SHELL` in the directory and compares what the loader loaded with what this scope should. A shell that runs no loader passes it, with a note. The check that the profile carries the block keeps its earlier name, `Env variables injected in shell profile`, rather than the `Env loader installed` first proposed on the issue: it still checks env.yaml against env.sh too, and `doctor --json` consumers read it by name.
- A team with `injectShellProfile: false` still registers its project, with no env.sh, so its directories load neither its env nor the user scope's. A user-scope team with it registers its line with no env.sh, so the user `env.sh` loads nowhere: not outside projects, not under a project that inherits the user scope. When no registered scope loads env after such a pull, no loader block goes in, but the pull still takes out, by the same all-or-nothing rule, every older block that sources this scope's `env.sh`, and for the user scope the inline-export block from before `env.sh` existed, which only the user scope wrote (project scopes came later); another scope's older block stays for its own pull to move. The one-time notice that user env no longer loads in projects counts that inline block as a user block.
- A user scope last pulled by an earlier version has no registry line. Any pull, a project's too, writes it when it is missing, from the user scope's config and its team's `injectShellProfile`, as a user-scope pull would. When either cannot be read, the line says opted out and the pull warns: the user `env.sh` stays out of shells until a user-scope pull. The loader still falls back to the user `env.sh` with no line, so an opted-in user scope keeps its env in shells across the upgrade.
- User-scope uninstall unregisters its scope; the last scope also removes the loader and registry and takes out their profile block. If registered projects remain, it removes the user line and keeps each project's data directory and registry entry, including when that entry is `-`; the loader stays only while some remaining entry loads env. These files join the ones a user-scope uninstall keeps for each project still set up (#1025): a registered partition counts as such a project, named like one with a config. Home-only uninstall, when no valid configuration is found, keeps the same set and removes the rest of `~/.teamai`.
- A registry that is missing reads as empty; one that exists but cannot be read is never taken for empty. The loader then loads no env in any directory, since it cannot tell which scope governs it. A pull fails with an error naming the file and does not rewrite it, so no other project's line is lost. Uninstall, user-scope or home-only, keeps the registry, the loader and all of `~/.teamai/projects`, and warns naming the file; project-scope uninstall keeps its line and the loader.
- The commands that decide the directory and its scope run as the shell or `PATH` has them, never as a function of the member's startup files: `builtin pwd`, `command git`, `command cygpath` and `command tr`.
- A project without env writes no block of its own, but when a profile file already carries a teamai block, its pull installs the loader and takes out the per-scope blocks, so an older version's user block stops loading in its directories. A profile file that exists but can't be read stops the pull with that error, and so does an unreadable `env.sh`; neither is taken as empty and overwritten. The migration is all or nothing: the loader block goes in and every older block comes out, or no profile file changes. A failed write puts back every file the pull already changed, and the pull reports the failure. Each profile file is planned and written once, at the file its links end at, so a `.zshrc` linked to `.zshenv` (or both linked into a dotfiles repo) keeps the loader block and stays a link. Putting a file back acts on the file its links end at: one the pull created, even behind a link that pointed at nothing yet, is removed with any directory the pull made for it, and the link is never removed.

## Limits

- Shells other than zsh and bash (fish, PowerShell, cmd) run no loader; `teamai env exec` covers them, and `doctor` names the gap wherever the directory delivers env, inherited user env included.
- With bash, a tool started outside a terminal (from a desktop app) gets nothing automatically; `teamai env exec` covers it.
- A project initialized by an earlier version and not touched since gets the user scope's env until a teamai command saves its config or a pull runs there: nothing marks it before then.
- With ZDOTDIR set, a login zsh whose `~/.zshenv` sets ZDOTDIR without sourcing `$ZDOTDIR/.zshenv` runs no loader itself; every zsh it starts does.
- zsh reads `.zshenv` before `.zshrc`: a key the member sets in `.zshrc` and the team also defines keeps the member's value in the shell it starts, and is not put back after a `cd` into another project and out.
- A project whose env files cannot be resolved is registered with no shell env for that pull, so its directories cannot fall back to user env. If registration fails, pull reports the project and fails.
- The one-time notice that user env no longer loads in projects is printed by the pull that migrates the profile; when that pull is the silent session-start one, only `~/.teamai/debug.log` keeps it.
- The session-start hint names project variables and inherited user-scope variables, with project declarations taking precedence.
- Windows (Git Bash, MSYS zsh, Cygwin) is covered by unit tests only, which run the loader under bash and zsh with a simulated `pwd`; CI has no Windows runner.
- On Windows, a shell with neither `pwd -W` nor `cygpath` resolves a directory under its own root (`/home/...`) to no project, so it gets the user scope's env there. Git for Windows, MSYS2 and Cygwin all ship `cygpath`.
